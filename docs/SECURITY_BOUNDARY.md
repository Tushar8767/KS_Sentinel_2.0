# KS Sentinel 2.0 — Security Boundary Specification

**Module:** 0 — Architecture Foundation  
**Status:** LOCKED SECURITY POLICY  

---

## 1. Browser Sandbox Limitations

Web browsers enforce strict security sandboxing to protect host systems from malicious scripts:
- **No Direct System API Access:** Browsers cannot directly interact with Windows APIs, inspect system hardware metrics, or manage host processes.
- **No Local File System Access Without User Grant:** Browser applications cannot arbitrary browse, read, or edit files on the host computer.
- **No Native CLI / Application Execution:** Browsers cannot directly execute binaries, open applications (like VS Code or Explorer), or manage Git CLI repositories.

---

## 2. Why a Local Sentinel Agent is Required

Because the web browser is sandboxed, remote access to local machine resources requires an out-of-browser bridge. 

The **Local Sentinel Agent** runs directly on the user's host machine as a background service/application. It acts as the authorized execution arm of KS Sentinel 2.0.

```text
Web OS Browser Client
        │  (Sandboxed HTTP/WS Requests)
        ▼
Server Gateway
        │  (Authenticated Capability Router)
        ▼
Local Sentinel Agent
        │  (Host API / Windows Executor)
        ▼
Local Host Machine Capabilities
```

---

## 3. Least Privilege & Controlled Access

KS Sentinel 2.0 enforces **Least Privilege** across all layers:
- The web client receives **only** the data necessary for the active view or window.
- The Local Agent operates under explicit user-defined permission boundaries (e.g. approved project folders, allowed applications).
- Access to resources is granted on a per-capability, per-path basis rather than providing global administrative rights.

---

## 4. Capability-Based Access vs. Unrestricted Execution

### Strict Prohibition of Arbitrary Execution
KS Sentinel 2.0 **strictly forbids** creating endpoints that accept arbitrary shell strings or raw terminal commands, such as:
- `POST /api/execute` (PROHIBITED)
- `exec(req.body.command)` (PROHIBITED)
- Unrestricted raw filesystem browsing endpoints (PROHIBITED)

### Capability-Based Model
All remote machine operations must be modeled as **explicit, strongly typed capabilities**.

Example capability message structure:
```json
{
  "capability": "GET_GIT_STATUS",
  "payload": {
    "projectPath": "D:/Projects/KS_Sentinel_2.0"
  },
  "requestId": "req_8f3a91b"
}
```

The Local Agent validates that `projectPath` is inside an authorized workspace before running the local Git CLI command. It returns structured JSON data rather than streaming an unparsed terminal session.

## 5. Future Authorization Flow

When a user or AI requests a sensitive action (e.g., launching an external tool, modifying files, or altering system settings), the request passes through the **Execution Broker**:

```text
1. Intent Generation (User action or AI request)
       │
2. Capability Formulation (Construct structured action payload)
       │
3. Gateway Authentication (Verify session token and client identity)
       │
4. Trust & Authority Check (Verify user privileges for capability)
       │
5. Policy Engine Evaluation (Validate target paths, risk score, time windows)
       │
6. User Approval (If action risk is MEDIUM or HIGH, prompt user for confirmation)
       │
7. Execution Broker Signing (Attach cryptographic authorization token)
       │
8. Local Agent Verification (Agent verifies signature & path boundaries)
       │
9. Safe Local Execution (Agent executes host API call)
       │
10. Audit Logging (Record action event in immutable audit log)
```

---

## 6. AI Guidance: AI is NOT Authority

- **AI Cannot Override Policy:** An AI agent cannot approve its own requests or grant itself expanded permissions.
- **AI Intent is Un-trusted:** Suggestions generated by AI models are treated as un-trusted inputs until validated by the Policy Engine and explicitly authorized by the user.
